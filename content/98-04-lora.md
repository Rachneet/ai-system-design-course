## What this explains

Sooner or later someone asks, "Should we fine-tune?" Usually the honest answer is "not yet": better prompts, retrieval and evals solve most problems faster, and they can be changed in an afternoon. This page shows what fine-tuning actually changes, using LoRA, the method most teams use when the answer is yes. It also explains why the [multi-tenancy lesson](#w9-tenancy) insists on one adapter per tenant, chosen by the gateway and never by the client.

## The idea: freeze the model, learn a small correction

A layer of a model multiplies its input by a weight matrix W. Full fine-tuning updates every number in W, for every layer: you need memory for the gradients and optimizer state of the whole model, and every fine-tune produces a full copy of it.

LoRA ([Hu et al., 2021](https://arxiv.org/abs/2106.09685)) freezes W and learns a correction made of two thin matrices, A and B, of rank r:

output = x W + (alpha / r) x A B

With r small (4 to 64 is typical), A and B together hold a tiny fraction of W's numbers. B starts at zero, so training starts exactly from the base model. After training you can merge the correction into W, so it adds no latency, or keep it separate and swap it per request. The paper reports that, against full fine-tuning of GPT-3 175B, LoRA can "reduce the number of trainable parameters by 10,000 times and the GPU memory requirement by 3 times", with "no additional inference latency".

## Run it

```bash
cd under-the-hood && uv sync
uv run python -m uth.lora
```

The script makes a 256 x 256 layer, gives two tenants data the base layer gets slightly wrong, and trains a rank-8 adapter for each by gradient descent on A and B only:

```text
Layer 256 x 256: full fine-tuning trains 65,536 numbers.
  LoRA rank  4:   2,048 trainable (3.1% of the layer)
  LoRA rank  8:   4,096 trainable (6.2% of the layer)
  LoRA rank 16:   8,192 trainable (12.5% of the layer)

acme: base model error 0.0174; after LoRA training 0.0000
globex: base model error 0.0165; after LoRA training 0.0000
acme's adapter on globex's data: error 0.0322. An adapter carries its tenant's behaviour.

Merged weights give the same output as base + adapter: True
Base weights untouched by training: True
One base (65,536 numbers) serves both tenants; each adapter adds 4,096.
```

The toy is kinder than reality: each tenant's change here really is low-rank, so a rank-8 adapter can learn it exactly. Real behaviour changes are only approximately low-rank, which is why rank is a setting you tune and evaluate. The two properties that matter for system design hold in general, though. The adapter learns the tenant's behaviour, which also means it can carry the tenant's data. And the base never changes, so many adapters can share one copy of it in GPU memory.

## When fine-tuning is the right tool

| The problem | Usually solved by | Fine-tune when |
|---|---|---|
| The model does not know your facts (policies, prices, products) | Retrieval: facts change, and retrieval updates in minutes with sources you can cite | Rarely: fine-tuned facts go stale and cannot be cited or deleted per user |
| The format or tone is wrong | Instructions, examples, structured outputs | A format must hold at scale and prompts that enforce it are long and costly |
| A narrow task is too slow or expensive on a large model | A smaller model with good prompts | A small model fine-tuned on the large model's outputs matches it on your task (distillation) |
| A task the model cannot do well at all | A different or larger model | You have thousands of good examples and an eval that proves the gain |

> [!rule] Fine-tune last, with an eval suite first. You need the suite to prove the fine-tune helped, to catch what it broke, and to rerun every time the base model changes underneath your adapter.

## What it changes in your designs

| Design decision | What LoRA explains | Where in the course |
|---|---|---|
| One adapter per tenant | An adapter trained on a tenant's data can repeat it, so it serves only that tenant | [Multi-tenancy](#w9-tenancy) |
| The gateway picks the adapter | Serving engines select an adapter by the request's model name, which the client controls; map keys to allowed adapters server-side (Switchboard's `allowed_models`) | [AI gateways](#w7-gateways) |
| Adapters are artifacts | Version them, record the base model and training data, and review them like any other deployed artifact | [Registries](#w8-registries) |
| Base model upgrades | An adapter fits one base model; a new base means retraining and re-evaluating every adapter | [Governance](#w10-governance) |
| Cost model | Serving many adapters on one base costs far less than one dedicated model per tenant | [AI FinOps](#w10-finops) |
