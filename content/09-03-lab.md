## What you will build

Relay has served one store, Northwind Outfitters, since Lab 1. In this lab it starts serving a second store, **Summit Cycles** (also fictional), from the same API, worker and database. Every customer read in Relay is already scoped by `customer_id` in SQL (`app/db.py`). That protects one customer from another inside a store. It does not protect one store from another, and a single forgotten filter would leak everything. You will add a boundary the database enforces.

**Acceptance criteria**

1. Every table that holds store data has a `tenant_id` column and a row-level security policy, and the API and worker connect as a role that is neither a superuser nor `BYPASSRLS`. Relay refuses to start otherwise.
2. The tenant comes only from a verified token claim. A token with no tenant, or an unknown one, gets a 401.
3. Retrieval, memory, sessions, orders, refunds, approvals, usage and feedback are scoped to the tenant by the database, not only by the code.
4. The knowledge-base search cache keys on tenant and principals; the same question from the two stores never shares an entry.
5. Each store calls models through its own Switchboard app with its own key and budget. Exhausting Summit's budget does not affect Northwind.
6. `tests/test_tenancy.py` runs as the app role and passes all eleven tests: cross-tenant reads by prompt injection, by direct API call, by retrieval, by memory and by cache all fail closed. The existing tests still pass, and `uv run ruff check .` is clean.

The code below is what you add: Relay's reference implementation does not contain it yet, so you are writing it, not copying it. Every function it calls exists in `relay/` today.

## Step 1: tenant columns, row-level security and an app role

### The schema

Relay applies `app/schema.sql` with idempotent statements only, so add a Lab 9 section at the end in the same style:

```sql
-- ---- Lab 9: tenants ------------------------------------------------------------------------------
CREATE TABLE IF NOT EXISTS tenants (
  id   text PRIMARY KEY,
  name text NOT NULL
);
INSERT INTO tenants (id, name) VALUES ('northwind', 'Northwind Outfitters') ON CONFLICT (id) DO NOTHING;

DO $$
DECLARE t text;
BEGIN
  FOREACH t IN ARRAY ARRAY['customers', 'orders', 'refunds', 'approvals', 'escalations', 'sessions', 'messages',
                           'memories', 'documents', 'chunks', 'ingest_jobs', 'reviews', 'usage_daily',
                           'idempotency_keys', 'feedback', 'online_judgements']
  LOOP
    -- Existing rows belong to the first store.
    EXECUTE format('ALTER TABLE %I ADD COLUMN IF NOT EXISTS tenant_id text NOT NULL DEFAULT %L REFERENCES tenants(id)',
                   t, 'northwind');
    -- New rows take the tenant of the transaction that writes them.
    EXECUTE format('ALTER TABLE %I ALTER COLUMN tenant_id SET DEFAULT '
                   'coalesce(nullif(current_setting(%L, true), %L), %L)', t, 'app.tenant_id', '', 'northwind');
    EXECUTE format('ALTER TABLE %I ENABLE ROW LEVEL SECURITY', t);
    EXECUTE format('ALTER TABLE %I FORCE ROW LEVEL SECURITY', t);
    EXECUTE format('DROP POLICY IF EXISTS tenant_isolation ON %I', t);
    EXECUTE format('CREATE POLICY tenant_isolation ON %I USING (tenant_id = current_setting(%L, true))',
                   t, 'app.tenant_id');
  END LOOP;
END $$;

CREATE INDEX IF NOT EXISTS orders_tenant ON orders (tenant_id, customer_id);
CREATE INDEX IF NOT EXISTS documents_tenant ON documents (tenant_id);
```

Read it closely, because each line carries a decision:

- **The policy** shows a row only when its `tenant_id` equals the transaction's `app.tenant_id`. With only a `USING` clause, Postgres applies the same condition to inserted and updated rows, so a Summit transaction cannot write a Northwind row. `current_setting(..., true)` gives NULL (or an empty string, once the setting has been used on a connection) when no tenant is set, and neither matches any row: a request with no tenant sees nothing.
- **The default** fills `tenant_id` from the transaction's tenant, so the existing `INSERT` statements in `app/db.py`, `app/ingest.py` and `app/seed.py` keep working unchanged. The `'northwind'` fallback exists only for jobs that run as the table owner (migrations, the existing tests); for the app role the policy's check still rejects any row whose tenant does not match the setting.
- **`FORCE ROW LEVEL SECURITY`** applies the policies to the table's owner too. Superusers still bypass them, whatever you write here.
- **Left out on purpose:** `jobs`, `rate_limits` and `flags` are platform tables. The worker claims jobs across all stores, rate-limit keys will carry the tenant, and flags are global kill switches.

### A role the policies apply to

Row-level security does nothing for a superuser, and Relay connects as `postgres` today. Create `infra/roles.sql`:

```sql
-- Run once per database as an administrator. The app and worker connect as relay_app; migrations stay with the owner.
CREATE ROLE relay_app LOGIN PASSWORD :'app_password' NOSUPERUSER NOBYPASSRLS;
GRANT USAGE ON SCHEMA public TO relay_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO relay_app;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO relay_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO relay_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT USAGE, SELECT ON SEQUENCES TO relay_app;
```

Now the API and the worker must stop applying the schema at startup, because DDL needs the owner. Delete the `await app.state.store.apply_schema()` line in `app/main.py`'s `lifespan` and `await store.apply_schema()` in `app/worker.py`'s `main`; `python -m app.migrate` is already the release step. In their place, refuse to run with RLS switched off. Add to `app/db.py`:

```python
async def assert_rls_applies(store: "Store") -> None:
    """Row-level security is silently off for superusers and BYPASSRLS roles. Refuse to serve as one."""
    async with store.conn() as c:
        row = await (
            await c.execute("SELECT rolsuper, rolbypassrls FROM pg_roles WHERE rolname = current_user")
        ).fetchone()
    if row["rolsuper"] or row["rolbypassrls"]:
        raise RuntimeError("connect as relay_app: this role bypasses row-level security")
```

Call it where the two `apply_schema` calls were. Then, from `relay/`:

```bash
docker compose up -d
uv run python -m app.migrate                       # as postgres, the owner: adds the columns and policies
docker compose exec -T db psql -U postgres -d relay -v app_password=change-me < infra/roles.sql
docker compose exec -T db psql -U postgres -d relay \
  -c "INSERT INTO tenants (id, name) VALUES ('summit', 'Summit Cycles') ON CONFLICT (id) DO NOTHING"
export RELAY_DATABASE_URL=postgresql://relay_app:change-me@localhost:5432/relay
```

> [!warn] Postgres documents that unique and foreign-key checks "always bypass row security". Relay's `orders.id`, `sessions.id`, `customers.id` and `documents.doc_id` are unique across all tenants, so a Summit request that tries to create a row with a Northwind ID gets a duplicate-key error, which tells it the ID exists. In this lab you keep IDs distinct and handle the one place a client chooses an ID (sessions, in Step 2). Composite keys are a stretch goal.

## Step 2: the tenant in every request

### From the token

In `app/auth.py`, add the tenant to `Principal` and read it from the verified claims. A missing or unknown tenant is an authentication failure, never a default:

```python

    customer_id: str
    tenant: str
    staff: bool = False
```


With a real identity provider, map its organisation claim to your tenant ID here. For development, give `mint` in `scripts/dev_token.py` a keyword argument `tenant: str = "northwind"` that it puts in the claims, and add a `--tenant` flag to both `scripts/dev_token.py` and `scripts/chat.py`. The default keeps the existing tests' tokens valid.

### Into every query

Every query in Relay goes through `Store.conn()`, which makes it the one place to set the tenant. In `app/db.py`, give the store an optional tenant and wrap each connection in a transaction that sets it:

```python
class Store:
    def __init__(self, source: AsyncConnectionPool | AsyncConnection, tenant: str | None = None):
        self.source = source
        self.tenant = tenant  # None: platform work (job claiming, migrations); RLS tables then show no rows

    def for_tenant(self, tenant: str) -> "Store":
        return Store(self.source, tenant)

    @asynccontextmanager
    async def _connection(self):
        if isinstance(self.source, AsyncConnectionPool):
            async with self.source.connection() as c:
                yield c
        else:
            yield self.source

    @asynccontextmanager
    async def conn(self):
        async with self._connection() as c:
            if self.tenant is None:
                yield c
                return
            async with c.transaction():  # the pool is autocommit: SET LOCAL alone would do nothing
                await c.execute("SELECT set_config('app.tenant_id', %s, true)", (self.tenant,))
                yield c
```

`set_config(..., true)` lasts only until the transaction ends, so a connection returned to the pool carries no tenant into the next request. Code that already opens `c.transaction()` inside `conn()` (refunds, approvals, `save_turn`, rate limits) gets a savepoint, which psycopg handles.

In `app/main.py`, derive a tenant store at the top of every endpoint that takes a `Principal`, and use it everywhere below, including in `Context(store=...)`:

```python
    store: Store = request.app.state.store.for_tenant(who.tenant)
```

Three more edits complete the path:

- **Rate limits.** `rate_limits` has no RLS, so put the tenant in the key: call `enforce_rate(store, f"{who.tenant}:{who.customer_id}", ...)` in `/chat` and `/emails`.
- **Sessions.** In `Store.load_session`, a session ID from another tenant is invisible, so the code tries to create it, and the primary key collides. Make the insert `INSERT ... ON CONFLICT (id) DO NOTHING RETURNING id` and raise `NotFound` when it returns nothing. The other tenant's session then looks exactly like a missing one, as the docstring already promises.
- **The prompt.** Give `system_prompt` in `app/prompts.py` a `tenant` parameter that picks `TENANTS[tenant].prompt` (read the files once at import), and pass `who.tenant` from `/chat` and `ctx.store.tenant` from `app/channels.py`.

## Step 3: tenant-scoped retrieval and memory

### Retrieval

`Retriever` keeps the store it was built with, and `app.state.retriever` is built with the untenanted one. Under RLS that is safe but useless: every search returns nothing. Add a method in `app/retrieval.py` that rebinds it per request:

```python
    def for_store(self, store: Store) -> "Retriever":
        return Retriever(store, self.embedder, self.reranker, self.candidates, self.cache)
```

and build the context in `/chat` and `/emails` with `retriever=request.app.state.retriever.for_store(store)`. The `VISIBLE` clause in `retrieval.py` already joins `documents` and filters by ACL; RLS now adds the tenant to both `chunks` and `documents` underneath it. Notice the shape of the safety: forgetting `for_store` gives empty results, not another store's documents.

### Ingestion

Both `reconcile` and `run_once` in `app/ingest.py` take a store, and `reconcile` takes a folder. In the worker's loop, run them once per tenant:

```python
        if since_reconcile >= reconcile_every:
            for t in TENANTS.values():
                await reconcile(store.for_tenant(t.id), t.kb_dir)
            since_reconcile = 0
        indexed = sum([await run_once(store.for_tenant(t), embedder) for t in TENANTS])
        done = indexed + await run_ready(store, jobs)
```

`reconcile` diffs a folder against the `documents` table and queues deletions for documents missing from the folder. Without a tenant boundary, reconciling `kb_summit/` would queue every Northwind document for deletion. With RLS, the Summit transaction cannot see Northwind's documents at all.

### Memory and other background jobs

Jobs are claimed by the platform (untenanted) store, so the payload must carry the tenant. In `Store.save_turn`, add `"tenant_id": self.tenant` to the payload; do the same where `/feedback` enqueues `judge_session`. In `app/worker.py`, run each handler as its tenant:

```python
    async def extract_memory(payload: dict) -> None:
        t = store.for_tenant(payload.get("tenant_id", "northwind"))  # jobs queued before this change
        session_id = UUID(payload["session_id"])
        messages = await t.load_session(session_id, payload["customer_id"])
        await remember(t, extractor, payload["customer_id"], session_id, messages)
```

and pass `store.for_tenant(payload.get("tenant_id", "northwind"))` to `online.judge_session`. Memories are now read and written under the tenant's policy; the `memories` lookup in `/chat` goes through the tenant store from Step 2.

## Step 4: tenant-keyed caches

Relay has no response cache yet, so add the one most teams add first: a short-lived cache of knowledge-base search results. Its key must hold everything that changes the answer. Add to `app/retrieval.py`:

```python
import time


class SearchCache:
    """In-process cache for search results. The key carries everything that changes the answer."""

    def __init__(self, ttl_s: float = 300, max_items: int = 10_000, clock=time.monotonic):
        self.ttl_s, self.max_items, self.clock = ttl_s, max_items, clock
        self.items: dict[tuple, tuple[float, list[Hit]]] = {}

    def key(self, tenant: str | None, principals: list[str], mode: str, k: int, query: str) -> tuple:
        if tenant is None:
            raise ValueError("refusing to cache a search that has no tenant")
        return (tenant, tuple(sorted(principals)), mode, k, " ".join(query.lower().split()))

    def get(self, key: tuple) -> list[Hit] | None:
        hit = self.items.get(key)
        return hit[1] if hit and self.clock() - hit[0] < self.ttl_s else None

    def put(self, key: tuple, hits: list[Hit]) -> None:
        if len(self.items) >= self.max_items:
            self.items.clear()  # bounded and crude; use an LRU or Redis in production
        self.items[key] = (self.clock(), hits)
```

Give `Retriever.__init__` a `cache: SearchCache | None = None` argument, build `app.state.retriever` in `lifespan` with `cache=SearchCache()`, and at the start of `Retriever.search` return a cached result for `self.cache.key(self.store.tenant, principals, mode, k, query)` when there is one; store the result before returning. The tests' retrievers have no cache, so nothing else changes.

Two questions to answer in your notes. Why must `principals` be in the key even though the tenant is? (Staff of the same store see `group:support` documents that customers must not.) What makes a cached result stale? (A document edit within the TTL; the stretch goals add the knowledge-base version to the key.)

The provider's prompt cache is the other cache in the path. Each store now has its own system prompt, so their cached prefixes differ from the first token. All stores still share your provider account's cache scope, as Lesson 2 explained; write down which of your tenants, if any, would need their own provider workspace or project.

Notes on the suite:

- **The injection tests script the model.** They assume the injection succeeded and check what the tools hand back, because a defence that depends on the model refusing is not a boundary. Week 3's eval suite tests whether the model resists; this suite tests what happens when it does not.
- **Order matters in the fixture.** Summit's documents are indexed after `SET ROLE`. Move the three Summit lines above it and run the suite again: as a superuser, `reconcile` sees Northwind's 30 documents, finds them missing from `kb_summit/`, and queues every one for deletion. The last test catches it. That is the bug RLS prevents in production.
- **Prove the suite can fail.** Comment out the `SET ROLE` line and run it: seven of the eleven tests go red, because the superuser bypasses every policy (and its reconcile wipes Northwind's index). The other four stay green, for a good reason: the `customer_id` filters already in `app/db.py`, the token checks and the request schema stop those attacks on their own. That is defence in depth working, and it is why the RLS tests must not rely on them. A security test you have never seen fail is a guess.

Finally, add a cross-tenant category to the evals: a few cases in `evals/cases/dev/redteam.yaml` where a Summit customer asks for Northwind's orders, documents or policies, and add the category to `must_never` in `evals/gates.yaml` next to `cross_customer`. The cases need the eval runner to mint Summit sessions; if yours cannot yet, record that as a known gap.

## Stretch goals

- **Composite keys.** Make `(tenant_id, id)` the primary key of `orders`, `customers`, `sessions` and `documents` with an expand-and-contract migration, and remove the covert channel from Step 1. Write down every foreign key that has to change.
- **Retrieval recall per tenant.** Load 20 more documents for Summit and 200 synthetic ones for a third tenant, then measure recall@3 per tenant with the vector mode. If small tenants lose recall, try `SET LOCAL hnsw.iterative_scan = relaxed_order` inside `Store.conn()` (pgvector 0.8.0 or later; check with `SELECT extversion FROM pg_extension WHERE extname = 'vector'`) and measure again.
- **Knowledge-base version in the cache key.** Add the tenant's latest `documents.updated_at` to the key, and a test that an edit invalidates the cache.
- **Fair limits.** Add a per-tenant bucket in front of the per-customer one with `take(store, f"tenant:{who.tenant}", ...)` from `app/limits.py`, sized so no store can use more than a quarter of your provider quota.
- **Per-tenant traces.** Add a `relay.tenant` attribute to the turn span next to `enduser.pseudo.id`, and a Grafana variable that filters every panel by it.
- **Tenants from the database.** Load `TENANTS` from the `tenants` table at startup, so onboarding a store is one row, one folder and one Switchboard app, not a code change.
